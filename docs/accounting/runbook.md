## Якщо `accountingStartAt` порожнє після вмикання

Причина: прапорець увімкнули на старій збірці без хука. Знімати й ставити прапорець не варто,
бо дата стане «зараз», а замовлення в проміжку стануть історичними. Краще записати фактичний час
вмикання: це `createdAt` першого замовлення з `accounting.stockTracked: true`.

```js
db.globals.updateOne(
  { globalType: 'accounting-settings', accountingStartAt: { $exists: false } },
  { $set: { accountingStartAt: ISODate('<createdAt першого облікового замовлення>') } }
)
```

## Резерв товару (В23)

Замовлення до відвантаження (`pending`, `paid`) тримає резерв: `stock-balances.reserved`, знімок у
`accounting.reservedItems`. Доступно = `qty − reserved`. Резерв не пише `stock-moves` і собівартість не змінює.

### Запуск міграції R9 (одноразово, відразу після деплою R4–R9)

Міграція `20261122_100000_reserve_pending_orders` резервує товар для наявних облікових замовлень.
До деплою фронтенд має вже знати статус `backorder` (`frontend-stock-notes.md`, розділ 4).

- [ ] Резервна копія БД (`mongodump`) безпосередньо перед міграцією; перевірити, що архів створено.
- [ ] Деплой коду (`pnpm build`, перезапуск, перевірка свіжої збірки як у кроці 0).
- [ ] `pnpm payload migrate:status`: у списку очікує лише `20261122_100000_reserve_pending_orders`.
- [ ] `pnpm payload migrate`. Усе йде однією транзакцією: при помилці нічого не змінюється.
- [ ] Прочитати звіт у лозі: `reservations: ... reserved N orders, moved M to backorder (<номери>)`.
      Замовлення зі списку `backorder` перевірити й за потреби повідомити клієнтам.
      Попередження `orders without items or warehouse skipped` означає, що замовлення без позицій
      чи складу пропущено: виправити його вручну в адмінці.
- [ ] `GET /api/stock/cache-check` (admin): порожній список розбіжностей.

Що робить міграція:

- У `stock-balances` без поля `reserved` ставить `reserved = 0`.
- Облікові непроведені замовлення в `pending`/`paid` без знімка резерву бере від найстарішого `createdAt`.
  Якщо вистачає доступного по всіх позиціях, резервує їх (`reservedAt = createdAt`); якщо ні, ставить
  `backorder` з переліком нестач і нічого не резервує. Тому старіші замовлення мають пріоритет.
- Історичні, проведені, скасовані й уже зарезервовані (створені після деплою) замовлення не змінює.
  Повторний запуск нічого не змінить.

Відкат (`pnpm payload migrate:down`): `reserved = 0` в усіх залишках, поля резерву прибрано з усіх замовлень,
`backorder` стає `pending` (колишні `paid` теж стануть `pending`, попередній статус не зберігається).
Резерви замовлень, створених після міграції, теж зникнуть. Надійніший відкат — із резервної копії.

### Віджет «Резерви» на дашборді

Бачать admin і manager. Дані з `GET /api/orders/reservation-summary`, рахуються при відкритті.

- **Прострочені резерви:** замовлення в `pending`/`paid`, у яких `reservedAt` старіший за
  `reservationDays` днів («Налаштування обліку»). Посилання відкриває відфільтрований список замовлень.
  Якщо `reservationDays` порожнє, строк не контролюється: лічильник 0, під плитками примітка про це.
- **Під замовлення:** кількість замовлень у `backorder`, посилання на їх список.
- **Перепродані позиції:** записи залишків, де `reserved > qty`. Admin переходить у звіт залишків
  (колонки «Зарезервовано», «Доступно» й позначка перепродажу), manager — у список «Залишки».

У формі простроченого замовлення є банер «Строк резерву минув DD.MM», у `backorder` — перелік нестач.

### Прострочений резерв

Після строку резерв не знімається сам. Менеджер з'ясовує з клієнтом:

- клієнт чекає — відвантажити, коли буде можливо, або залишити як є;
- клієнт відмовився — admin скасовує замовлення, резерв знімається, товар знову доступний;
- товар потрібен іншим — перевести замовлення в `backorder` (з `pending` може manager, з `paid` лише admin):
  резерв знімається, нестачі зафіксовано. Повернути в `pending` можна, коли товару знову вистачає.

### Перепродані позиції (`reserved > qty`)

Виникають, коли інвентаризація списала товар нижче резерву (дозволено, але не нижче 0). Замовлення
з резервом на такий товар не відвантажиться: відвантаження перевіряє доступне.

1. У звіті залишків знайти позицію з позначкою перепродажу, у списку замовлень — замовлення з цим товаром у `pending`/`paid`.
2. Оприбуткувати закупівлю або переміщення, якщо товар очікується.
3. Інакше перевести частину замовлень у `backorder` (почати з найновіших), доки `reserved ≤ qty`,
   або змінити в них позиції чи склад, або скасувати.

### Перевірка кешу резерву

`GET /api/stock/cache-check` (admin) звіряє `reserved` кожного запису залишків із сумою
`accounting.reservedItems[].qty` замовлень у `pending` і `paid` за тим самим товаром і складом. Розбіжність має
вигляд `{ type: 'reserved', product, warehouse, expectedReserved, actualReserved }`. `POST /api/stock/cache-rebuild`
ставить `reserved = expectedReserved` (запис без резервів — 0). Запускати в неробочий час: замовлення, що
зберігаються паралельно, дають хибні розбіжності. Перед rebuild з'ясувати причину: розбіжність резерву
означає, що резерв змінили повз сервіс складу.
