# Запуск обліку складу: чек-лист (S2.8)

Дизайн: `docs/accounting/design.md`, розд. 10 (кроки 0-6) і ризик Р1. Процедура одноразова,
у неробочий час. Виконує власник з роллю admin; розробник готує код і репетицію.

Область: облік товару (склад). Каси, борги й фінанси сюди не входять (етап 3).

## 0. Підготовка (розробник)

- [ ] Код етапів 1-2 розгорнуто, `stockControlEnabled = false`. Замовлення створюються як раніше.
- [ ] Прод працює на replica set (D6). Перевірка в `mongosh` на проді:

  ```js
  db.hello().setName   // має повернути ім'я набору, не undefined
  ```

  Якщо `undefined`, це standalone: умовне списання не відкотиться разом із замовленням.
  Прапорець `stockControlEnabled` не вмикати, спершу перейти на replica set.
- [ ] Міграції застосовано: склади `main`, `shop` і `defaultWebWarehouse = main` існують.
- [ ] Резервну копію БД знято безпосередньо перед кроком 6.

## Репетиція на копії прод-БД (обов'язково до реального запуску)

- [ ] Відновити дамп прод-БД в окрему базу (не `cosmetics_test`, не прод) на replica set.
- [ ] Пройти кроки 1-6 нижче на цій копії, включно з імпортом CSV та вмиканням прапорця.
- [ ] Створити тестове замовлення з сайту й з адмінки: залишок зменшився, у `stock-moves` є рухи,
      у `accounting` замовлення заповнені `stockPostedAt` і `cogsBani`.
- [ ] Скасувати його: залишок повернувся.
- [ ] Нестача: замовлення більше за залишок ⇒ 409 `INSUFFICIENT_STOCK`, замовлення в БД немає.
- [ ] `GET /api/stock/cache-check` (admin) повертає порожній список розбіжностей.
- [ ] Зафіксувати час кожного кроку й помилки імпорту (невідомий артикул, дублі, `qty <= 0`, `cost <= 0`).

## 1. Довідники (admin)

- [ ] Склади `main`, `shop` активні; у «Налаштуваннях обліку» `defaultWebWarehouse`
      (і за потреби `defaultAdminWarehouse`).
- [ ] Постачальники, якщо вже відомі.

## 2. Дата відсічення T (власник)

- [ ] Обрано T (кінець робочого дня).
- [ ] Після T до кроку 6 нові замовлення в адмінці не вводяться. Сайт можна лишити:
      замовлення до вмикання не списують залишок і вважаються історичними.

## 3. Підрахунок залишків на T (власник)

- [ ] Залишок кожного товару по кожному складу: артикул, склад, кількість.
- [ ] Початкова собівартість кожного товару із залишком, MDL за шт., 2 знаки. Без неї середня
      не стартує. Якщо невідома: остання ціна закупівлі; запасний варіант `wholesalePrice × коефіцієнт`,
      узгоджений власником.

## 4. Імпорт початкових залишків (admin)

- [ ] CSV: `article; warehouseCode; qty; unitCostMDL`.
- [ ] `scripts/import-opening-stock.ts` створює чернетку `opening-balances` kind=stock і звіт помилок.
      Скрипт лише створює чернетку, нічого не проводить.
- [ ] Усі помилки зі звіту виправлено, імпорт повторено.

## 5. Інші початкові документи (admin, етап 3)

- [ ] Лише коли є етап 3: залишки кас, борги постачальникам, борги клієнтів. Для запуску складу не потрібні.

## 6. Проведення і вмикання (admin)

- [ ] Чернетки перевірено (кількості, собівартості, склади).
- [ ] Повторно перевірено `db.hello().setName` на проді.
- [ ] Усі `opening-balances` kind=stock проведено.
- [ ] Залишки в «Залишках» збігаються з підрахунком власника (вибірково по 10-20 товарах).
- [ ] У «Налаштуваннях обліку» увімкнено `stockControlEnabled` і в тому ж збереженні задано `accountingStartAt = now`.
      Увага: поле `readOnly` в адмінці, а автоматично його код поки не ставить (немає хука на глобалі).
      До окремої задачі виставити через Local API одним `updateGlobal` разом із прапорцем.
- [ ] Замовлення сайту, що надійшли між T і вмиканням: ввести як списання (`writeoff`)
      або скоригувати через інвентаризацію.
- [ ] Контрольне замовлення з сайту: залишок зменшився, відповідь `createOrder` без змін.

## Відкат

- Зняти `stockControlEnabled`: нові замовлення перестають списувати, проведені лишаються проведеними.
- Повне відновлення лише з резервної копії кроку 0; замовлення, створені після копії, переносяться вручну.
