# Резерв товару: проєкт змін для фронтенду (В23)

Дата: 2026-11-22. Бекенд: задачі R4, R7 у `docs/accounting/reservation-tasks.md`.
Доповнює `docs/accounting/frontend-stock-notes.md`. Після реалізації R10 переносить зміни туди.

**Коротко:** нових ендпоінтів і полів запиту немає. Змінюється значення `inStock` і `available` у 409,
а в історії замовлень покупця з'являється новий статус `backorder`. Сумісність зламана лише в одному місці:
фронтенд, що не знає `backorder`, покаже сирий статус. Тому пункт 3 треба викотити **до** або **разом** із бекендом.

---

## 1. `inStock` враховує резерв

Ендпоінти й формат не змінюються (розділ 1 `frontend-stock-notes.md`). Змінюється лише значення:

| Було (В4) | Стало (В23) |
|---|---|
| `true`, якщо `qty > 0` на складі сайту | `true`, якщо `qty − reserved > 0` на складі сайту |

Що з цього випливає:

- Товар стає «немає в наявності» вже тоді, коли інші покупці оформили на нього замовлення, а не лише після відвантаження.
- Товар може повернутися в наявність без закупівлі: досить, щоб замовлення скасували.
- `inStock` змінюється частіше, ніж раніше.

**Що зробити:**

- [ ] Якщо каталог кешується (ISR, `revalidate`, CDN), скоротити час кешу сторінок товару й каталогу або перевіряти `inStock` при відкритті кошика. Остаточна перевірка все одно відбувається при створенні замовлення (пункт 2).
- [ ] Логіка показу не змінюється: «немає в наявності», якщо `unavailable === true` або `inStock === false`, і кнопка «у кошик» вимкнена.

## 2. `POST /api/orders/create` → 409: доступне з урахуванням резерву

Формат відповіді не змінюється:

```json
{
  "success": false,
  "code": "INSUFFICIENT_STOCK",
  "message": "Some items are not available in the requested quantity",
  "items": [{ "product": "<id>", "requested": 3, "available": 1 }]
}
```

Що змінилося:

- `available` тепер означає **вільний** залишок (`qty − reserved`), так само наближений (кратне 5, мінімум 1, гостю не віддається).
- Замовлення сайту, створене успішно, **резервує товар**: інший покупець цей товар уже не замовить.
- Сайт ніколи не отримує статус `backorder`. При нестачі, як і раніше, приходить 409, і замовлення не створюється.

409 тепер виникатиме частіше: кошик зібрали, поки товар був вільний, а хтось оформив замовлення раніше.

**Що зробити:**

- [ ] На 409 з `code === 'INSUFFICIENT_STOCK'` показати в кошику, яких позицій бракує (за `items[].product`), і не втрачати кошик.
- [ ] Авторизованому покупцеві запропонувати зменшити кількість до `available`. Якщо `available === 0`, запропонувати прибрати позицію.
- [ ] Гостю показати «немає в потрібній кількості» без числа.
- [ ] Після 409 перезапросити товари кошика, щоб оновити `inStock`.
- [ ] Свій текст повідомлення, орієнтуючись на `code`, а не на `message`.

## 3. Новий статус `backorder` в історії замовлень

`GET /api/orders/my` повертає `status`. Значення тепер такі:

| `status` | Що означає для покупця | Текст (пропозиція) en / ru / ro |
|---|---|---|
| `pending` | прийняте, товар відкладено | Accepted / Принят / Acceptată |
| `paid` | оплачене, товар відкладено | Paid / Оплачен / Achitată |
| **`backorder`** (новий) | прийняте, частини товару немає, чекаємо надходження | On order / Под заказ / La comandă |
| `shipped` | відправлене | Shipped / Отправлен / Expediată |
| `cancelled` | скасоване | Cancelled / Отменён / Anulată |

Звідки береться `backorder`: менеджер оформив замовлення на покупця в адмінці (телефоном, у магазині), а товару не вистачило. Коли товар надійде, менеджер переведе його в `pending`. Покупець після цього побачить `pending`, а згодом `shipped`.

Перелік нестач (`shortages`) і дані резерву покупцеві **не віддаються**: `getNormalizedOrders` повертає фіксований набір полів, і він не змінюється.

**Що зробити:**

- [ ] Додати `backorder` у мапу статусів (бейдж, колір, переклади en/ru/ro).
- [ ] Для `backorder` показати підказку: «Частина товару очікується, менеджер зв'яжеться з вами, щойно замовлення буде готове».
- [ ] Невідомий статус показувати нейтральним бейджем без збою, на випадок нових статусів у майбутньому.
- [ ] Викотити **до** або **разом** із бекендом (міграція R9 може одразу перевести наявні замовлення в `backorder`).

## 4. Що для фронтенду не змінюється

- Ендпоінти, параметри й авторизація.
- Строк резерву (`reservationDays`) і сповіщення про нього бачать лише admin і manager в адмінці. Сайт їх не отримує.
- Скасування замовлення як і раніше робить тільки admin. У покупця кнопки скасування немає.
- `GET /api/stock/product/:id` (поля `reserved`, `available`) лише для адмінки. Сайт його не викликає.

2. [ ] Бекенд: R4–R7 і міграція R9.
3. [ ] Фронтенд: пункт 1 (кеш каталогу) за результатами перших днів на проді.
4. [ ] Перевірка на проді:
   - два браузери замовляють останню одиницю: перший отримує 201, другий 409, після чого `inStock = false`;
   - скасування першого замовлення в адмінці повертає `inStock = true`;
   - замовлення, оформлене в адмінці при нестачі, покупець бачить як «Под заказ».
